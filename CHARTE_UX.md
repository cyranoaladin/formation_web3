🎓 RBK Labs — Charte UX Officielle

Version : 1.0 (Production)
Audience : étudiants avancés, mentors, auditeurs, builders Solana/Web3

1. Philosophie UX
1.1 Principe fondamental

RBK Labs n’est pas une plateforme éducative grand public.
C’est un environnement de travail technique, comparable à :

un espace d’audit de sécurité

un IDE mental

un laboratoire de protocoles

👉 L’UX doit respecter l’intelligence de l’utilisateur, jamais la sur-simplifier.

1.2 UX ≠ Gamification

RBK Labs refuse :

badges enfantins

animations inutiles

récompenses artificielles

effets “hype crypto”

👉 La motivation vient de la maîtrise, pas du divertissement.

1.3 UX comme preuve de sérieux

L’UX est un signal de crédibilité pour :

étudiants seniors

mentors techniques

recruteurs

investisseurs

Si l’interface ressemble à une plateforme “MOOC”,
👉 le projet est déjà en échec.

2. Cibles Utilisateurs
2.1 Étudiant RBK

Profil :

développeur Solana / Rust / Anchor

logique d’ingénieur

accepte la complexité si elle est cohérente

Attentes UX :

clarté de l’état du système

accès direct aux preuves (tests, logs, diff)

aucun bruit inutile

2.2 Mentor / Reviewer

Profil :

auditeur

senior engineer

reviewer technique

Attentes UX :

vitesse

densité informationnelle

outils précis (rubrics, artefacts, diff)

2.3 Agent IA (builder / reviewer)

RBK Labs est AI-native.

👉 Toute UX doit être :

lisible par un humain

structurable par un agent IA

déterministe (pas d’ambiguïté visuelle)

3. Principes UX Non-Négociables
3.1 Clarté de l’état système

À tout moment, l’utilisateur doit savoir :

où il est

ce qui s’exécute

ce qui a échoué

ce qui attend une action humaine

Aucun état implicite.

3.2 Densité contrôlée

RBK Labs accepte une UX dense, mais :

jamais confuse

jamais décorative

toujours hiérarchisée

👉 Moins d’espace blanc, plus de sens.

3.3 Lisibilité avant esthétique

Une interface belle mais floue est une faute grave.

Priorité stricte :

Compréhension

Auditabilité

Esthétique

3.4 Neutralité émotionnelle

Le ton UX est :

neutre

professionnel

sobre

Pas de :

“Congratulations 🎉”

“Oops 😅”

emojis

4. Langage Visuel
4.1 Thème

Dark-first

éclairage maîtrisé

contrastes fonctionnels

Le dark mode n’est pas décoratif :
👉 il évoque outil de travail et console experte.

4.2 Couleurs

Règles :

palette restreinte

couleurs signifiantes

aucune couleur “juste parce que c’est joli”

Exemples de sémantique :

Vert : succès validé

Orange : en cours / attention

Rouge : échec / bloquant

Bleu froid : information / état neutre

4.3 Typographie

Sans-serif moderne pour structure

Monospace pour :

code

hashes

IDs

logs

proofs

Lisibilité > originalité.

4.4 Icônes

fines

techniques

outline uniquement

Jamais :

icônes illustratives

emojis

pictogrammes “ludiques”

5. Architecture UX (Navigation)
5.1 Navigation globale

Sidebar persistante

Accès direct aux sections critiques

Pas de profondeur inutile (> 3 niveaux = erreur)

5.2 Pages principales obligatoires

Student Dashboard

Labs Interface

Submission View

Mentor Dashboard

RAG Search

Chaque page a :

un rôle unique

un objectif clair

des actions explicites

6. UX des Labs (Cœur du produit)
6.1 Le Lab n’est pas un cours

Un Lab RBK est :

une mission

un audit

un exercice de responsabilité

Donc :

pas de narration enfantine

pas de storytelling inutile

structure claire et sèche

6.2 Structure d’un Lab

Toujours visible :

Objectifs

Contraintes

Deliverables

Rubric

État des soumissions

L’étudiant ne “découvre” rien par hasard.

6.3 Soumission

ZIP only

statut visible immédiatement

feedback progressif (tests → review)

UX orientée process industriel, pas devoir scolaire.

7. UX du RAG (Recherche de connaissance)
7.1 Pas un chatbot

Le RAG RBK :

ne simule pas une conversation

ne “parle” pas de façon humaine

Il répond par documents, preuves et citations.

7.2 Structure RAG

Query → Résultats classés

Citations visibles

Sources identifiables

Confiance affichée

👉 UX de recherche technique, pas d’assistant bavard.

8. États, Erreurs, Feedback
8.1 États explicites

Chaque action peut être :

en attente

en cours

terminée

bloquée

Chaque état est :

visible

horodaté

explicable

8.2 Erreurs

Une erreur RBK :

explique le pourquoi

ne minimise pas le problème

ne culpabilise pas l’utilisateur

Pas de :

“Something went wrong”

“Try again later”

9. Accessibilité & Robustesse

lisible sans animations

utilisable sur écran large (desktop-first)

aucune dépendance à un effet visuel critique

L’UX doit survivre :

à un mauvais réseau

à un backend lent

à un agent IA utilisateur

10. UX comme Contrat
10.1 Pour les développeurs

Toute implémentation UI qui viole cette charte est non conforme, même si elle fonctionne.

10.2 Pour les agents IA

Cette charte est :

une règle Always-On

un filtre de décision UX

Si une proposition UX est :

ambiguë

décorative

“marketing”

👉 Elle doit être rejetée.

11. Conclusion

RBK Labs n’optimise pas pour :

la séduction

la facilité

la viralité

RBK Labs optimise pour :

la compétence

la responsabilité

la crédibilité long terme

L’UX est au service de la maîtrise.
